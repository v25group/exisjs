# ExisJS Release v0.10.3

**Status:** Released 2026-11-13 (npm tag `latest`)  
**Type:** Patch: cron scheduling, the development server, slow request bodies  
**Affected Packages:** `exisjs`, `@exisjs/cli`, `create-exisjs`

**Upgrade if you have a cron job that runs monthly, quarterly, yearly or on set weekdays, or an interval longer than 24 days.** Such a job could run many times a second, and a monthly or weekly job could skip a whole month or week.

A client sending a request body a few bytes at a time could also hold a connection for 5 minutes on Node.js, and indefinitely on uWebSockets.js and Bun. The new `requestTimeout` setting cuts it off after 60 seconds.

---

## Behaviour changes

Each is a fix, but a running app can notice it. Check the ones that apply before upgrading.

1. **`exisjs dev` no longer polls for file changes on Windows by default.** Polling reported every file as changed when it started, so the server restarted about 4 seconds after starting, and crons and `onStart` hooks ran twice. Native file events work on local disks, Windows included.
   **Migrate:** on a network drive, a WSL mount or a Docker volume, set `dev: { usePolling: true }` in `exis.config.ts`.
2. **Source folders named like data folders reload.** `dist`, `build`, `out`, `test`, `tests`, `coverage`, `downloads`, `storage`, `uploads`, `logs`, `data`, `fixtures`, `reports`, `artifacts` and `public` are ignored only at the project root. Before, they were ignored anywhere, so an edit in `src/http/api/reports/service.ts` never reloaded and the old code kept running without any message.
3. **Files named `tmp-*` or `scratch-*` don't reload the dev server**, so a one-off script created and deleted next to the code doesn't restart it.
4. **A request must arrive within 60 seconds.** The new `requestTimeout` setting (default `60_000` ms) covers the headers and the whole body. A handler that takes longer after the request has arrived isn't affected. On Node.js the client gets `408` and the connection closes; on uWebSockets.js the connection closes; on Bun the request answers `408 REQUEST_TIMEOUT`.
   **Migrate:** for large uploads over slow connections, raise it, for example `requestTimeout: 10 * 60_000`. `0` turns it off.
5. **`inject()` returns `set-cookie` as an array**, one entry per cookie, as `node:http` and the response type already said. It used to join them with commas, which can't be split again because cookie dates contain commas. `.expect('set-cookie', value)` passes when any one cookie matches.
   **Migrate:** a test reading `res.headers['set-cookie']` as a string: use `res.headers['set-cookie'][0]`, or `.join('; ')`.
6. **The reload line names what happened:** `reloading: src/http/api/users/route.ts changed (+2 other files: 1 added, 1 deleted)` instead of `reloading due to change in ...`.

## Fixed

### Security

- **A slow request body held a connection.** ExisJS never set Node's `requestTimeout`, so a client sending a body one byte at a time kept the connection for Node's default 5 minutes. On uWebSockets.js and Bun, which only close idle connections, it never ended. A few hundred such clients use up a server's connections. `requestTimeout` (60 s by default) now bounds it on all three: Node's own setting, plus a deadline on reading the body in the uWS and Bun adapters.

### Testing

- **`inject()` joined repeated `Set-Cookie` headers** into one string (B27). It now returns them as an array.

### Cron

- **A job whose next run was more than 24.8 days away ran in a loop.** One `setTimeout` waited for the next run, and Node.js turns any delay longer than 2,147,483,647 ms into 1 ms, with only a `TimeoutOverflowWarning`. The job ran, scheduled the same delay again and ran again, many times a second. Long waits now go in steps, and a job never runs before its time. Long `interval` and `timeout` jobs had the same problem.
- **A monthly, yearly or weekly job could skip a month, year or week.** The next run was searched by jumping 12 hours over days that didn't match, which could land past the right hour of the right day. Whether it did depended on the time of day the server started, in every time zone, UTC included: `30 3 1 * *` with `timezone: 'Asia/Kolkata'`, started on 13 November, next ran on 1 January instead of 1 December. Compared with a minute-by-minute search over 480 cases (10 patterns, 8 time zones including daylight-saving ones), the old search was wrong in 171 and the new one in none.
- **A failed job was logged without its error.** `Unhandled error in cron job "sync"` showed only the job name and duration. The error is now logged as an object, so the message and stack reach the log. This also applies to lock errors, `onError` hook errors, cron files that fail to load and lifecycle hook errors.

### Logging

- **Pretty logs hid the error of any line that wasn't a request.** `log.error({ err }, 'Import failed')` printed only `Import failed` in development. The error's message and its first four stack frames now follow on the next lines. JSON logs in production already included it.

### Development server

- **A restart could fail with "Port 4000 is already in use".** When TypeScript reported errors, `exisjs dev` started its build-error page on the app's port even while the app was running. On the next restart that page could take the port before the new app process did. The error page now starts only when the app process isn't running. Each restart also waits for the old process and the error page to release the port, and if the port is still taken, it says who holds it and tries again up to three times.
- **Restarting after a crash waited 3 seconds** for a process that had already exited.
- **`.exis/dev-status.json` said `"status": "ok"` while the terminal showed errors.** It now holds the server's PID, start time and restart count, the last crash and the current type errors, with `status: 'error'` while either exists. An editor, a script or an AI agent working in the project can read it to check that its change was picked up.

## Checks

- 1118 tests (1117 pass, 1 Linux-only skipped); 28 new. Without the fixes, 6 of the 10 new cron and logging tests fail, and 6 of the 10 new timeout and `Set-Cookie` tests fail (on the old code a trickled body kept the connection open on Node.js and uWebSockets.js for the whole 8-second test, and on Bun the body never ended).
- `exisjs dev` on `examples/01-my-app` on Windows, with polling off and on, 11 checks each: no restart after start, an edit in `src/http/reports` reloads, `tmp-*` files don't, a type error keeps the app serving and shows in `dev-status.json`, 10 fast file create and delete cycles with type errors present cause no "already in use", fixing the error sets `status` back to `ok`.

## Upgrade

```bash
npm install exisjs@0.10.3
npm install -D @exisjs/cli@0.10.3
```

`@exisjs/fetch` stays at 0.9.2: its code didn't change.

If you set `dev: { usePolling: false }` to stop the restart after start, you can remove it. If you added `ignored` patterns for `tmp-*` scripts, they are now ignored by default.
