# Error Handling

ExisJS implements a comprehensive error boundary and observability system. The framework is designed to reduce the need to manually construct HTTP error responses.

## The `HttpError` System

You can throw an `HttpError` anywhere in your application, and the ExisJS router will automatically intercept it, log it, and format it into a standardized JSON response for the client.

### Functional Paradigm

```typescript filename="src/http/users/route.ts"
import { controller, route } from 'exisjs/router'
import { HttpError } from 'exisjs/error'

export default controller({
  getUser: route.get('/:id', {
    async handle({ params }) {
      const user = db.findUser(params.id)
      
      if (!user) {
        // This stops execution and returns a 404
        throw HttpError.notFound('User') 
      }
      
      if (user.isBanned) {
        // This returns a 403 Forbidden
        throw HttpError.forbidden('User is banned from the platform')
      }

      return { user }
    }
  })
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/users/route.ts"
import { Controller, Get, Param } from 'exisjs/decorators'
import { HttpError } from 'exisjs/error'

@Controller()
export default class UsersController {
  @Get('/:id')
  async getUser(@Param('id') id: string) {
    const user = db.findUser(id)
    
    if (!user) {
      // This stops execution and returns a 404
      throw HttpError.notFound('User') 
    }
    
    if (user.isBanned) {
      // This returns a 403 Forbidden
      throw HttpError.forbidden('User is banned from the platform')
    }

    return { user }
  }
}
```

### Common Error Factories

The `HttpError` class provides static factory methods for standard HTTP status codes:

- `HttpError.badRequest('Message')` - 400
- `HttpError.unauthorized('Message')` - 401
- `HttpError.forbidden('Message')` - 403
- `HttpError.notFound('Resource')` - 404
- `HttpError.conflict('Message')` - 409
- `HttpError.payloadTooLarge('Message')` - 413
- `HttpError.unprocessable('Message', details)` - 422
- `HttpError.rateLimit('Message')` - 429
- `HttpError.internal('Message')` - 500

### Direct Error Classes & Exceptions

If you prefer a class-based approach, ExisJS exports every standard error as its own class. We also provide `Exception` aliases for every error class. You can import and throw them directly:

```typescript filename="example.ts"
import { 
  NotFoundException, 
  UnauthorizedException, 
  BadRequestError, 
  PayloadTooLargeError 
} from 'exisjs/error'

export const uploadMedia = (req, res) => {
  if (req.headers['content-length'] > 10 * 1024 * 1024) {
    throw new PayloadTooLargeError('File exceeds 10MB limit')
  }
}
```

### The Standardized Response

When an `HttpError` is thrown, the client will automatically receive a structured JSON payload.

```json filename="Response"
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "User not found"
  }
}
```

### Validation Error Responses & Diagnostic Visibility

When schema validation fails (via `tex`, Zod, or Yup), ExisJS produces a typed `400 Bad Request` featuring a clean `errors: Record<string, string>` map for seamless frontend form field binding:

```json filename="HTTP 400 Bad Request Response"
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Validation Error: email: Invalid email format, age: Field must be >= 18",
  "errors": {
    "email": "Invalid email format",
    "age": "Field must be >= 18"
  }
}
```

#### Development Terminal Diagnostics

In development mode, ExisJS automatically outputs formatted tabular diagnostics to the terminal displaying the exact HTTP part, field, received value, and expected requirement:

```text
[VALIDATION FAILED] POST /auth/register (part: body)
┌─────────────┬───────────────────────────┬──────────────────┐
│ Field       │ Received                  │ Expected         │
├─────────────┼───────────────────────────┼──────────────────┤
│ email       │ "alice"                   │ Valid email      │
│ age         │ "16"                      │ min: 18          │
└─────────────┴───────────────────────────┴──────────────────┘
```

If you throw an unhandled exception (like a database connection failure or a `TypeError`), ExisJS catches it and securely returns a `500 Internal Server Error`, hiding the stack trace from the client in production mode while logging the full trace to your internal logger.

## Error Handling Decision Tree

To keep your codebase clean and consistent, use this decision tree when deciding how to handle errors:

1. **Is it a known client error (e.g., missing parameter, forbidden)?**
   👉 **Throw an `HttpError` directly.** Let the framework format the 4xx response automatically.
2. **Do you need to intercept an unexpected failure (e.g., Database Connection failure) globally?**
   👉 **Use an Exception Filter (`catchError`) in `server.ts`.** Map the specific exception class to a 5xx response.
3. **Do you need to intercept errors only for a specific route group (e.g., Admin Panel)?**
   👉 **Use Local Error Hooks (`onError`) in the gateway/controller.** Keep the logic isolated to that specific module.
4. **Is it standard 4-arg middleware from the Express ecosystem?**
   👉 **Use `app.use(errorHandler)`** (where `errorHandler = (err, req, res, next) => {}`). ExisJS supports standard Connect/Express error middleware natively.

## Extended Error Handling

ExisJS provides mechanisms for granular and centralized error handling.

### 1. Framework-Level Exception Handler (`src/http/error.ts`)

Instead of writing manual `try/catch` blocks in every route or wiring `app.onError` inside `server.ts`, ExisJS provides a dedicated file convention: **`src/http/error.ts`** (or `src/http/*.error.ts`).

When `src/http/error.ts` is present, ExisJS automatically discovers and mounts it during application boot as the global exception interceptor. Any uncaught exception, thrown `HttpError`, or validation failure anywhere in your application is routed to this file.

#### Functional Paradigm

```typescript filename="src/http/error.ts"
import type { Request, Response } from 'exisjs'
import { isDev } from 'exisjs/config'

/**
 * Global Framework Exception Handler
 * Auto-mounted at startup to intercept all unhandled exceptions and validation errors.
 */
export function onError(err: any, req: Request, res: Response) {
  const status = err.statusCode || err.status || 500
  const isOperational = Boolean(err.isOperational || err.statusCode < 500)

  // 1. Log unexpected crashes in production to external APM (Sentry, Datadog, Axiom)
  if (!isOperational && !isDev) {
    // e.g. Sentry.captureException(err, { extra: { path: req.path, method: req.method } })
    req.log.error({ err }, '[Fatal] Unhandled Server Exception')
  }

  // 2. Format a unified, standard error envelope for client applications
  res.status(status).json({
    success: false,
    error: {
      code: err.code || (status === 500 ? 'INTERNAL_SERVER_ERROR' : 'ERROR'),
      message: err.message || 'Internal Server Error',
      ...(err.details ? { details: err.details } : {}),
      ...(err.errors ? { errors: err.errors } : {}),
      path: req.path,
      timestamp: new Date().toISOString(),
    },
  })
}
```

#### Class-Based (OOP) Paradigm

```typescript filename="src/http/error.ts"
import type { Request, Response } from 'exisjs'
import { isDev } from 'exisjs/config'

export default class GlobalErrorHandler {
  onError(err: any, req: Request, res: Response) {
    const status = err.statusCode || err.status || 500
    const isOperational = Boolean(err.isOperational || err.statusCode < 500)

    if (!isOperational && !isDev) {
      req.log.error({ err }, '[Fatal] Unhandled Server Exception')
    }

    res.status(status).json({
      success: false,
      error: {
        code: err.code || (status === 500 ? 'INTERNAL_SERVER_ERROR' : 'ERROR'),
        message: err.message || 'Internal Server Error',
        ...(err.details ? { details: err.details } : {}),
        path: req.path,
        timestamp: new Date().toISOString(),
      },
    })
  }
}
```

> [!TIP]
> **Scaffold with CLI**: You can generate this file instantly using the ExisJS CLI:
> ```bash
> npx exis generate error
> # or shorthand:
> npx exis g error
> ```

#### What `src/http/error.ts` Intercepts:
- **`HttpError` instances**: (e.g. `throw HttpError.notFound()`, `throw HttpError.unauthorized()`).
- **Validation failures**: Zod, Tex, or Yup validation rejections automatically pass structured `err.errors` and `err.details`.
- **Database / Network exceptions**: Postgres connection failures, timeout rejections, and third-party API errors.
- **Syntax errors**: Malformed JSON bodies or bad request payloads.


### 2. Exception Filters (`catchError`)

ExisJS allows you to create **Exception Filters** to globally intercept specific types of errors. 

Using the `catchError` middleware, you can map specific custom errors to custom responses globally:

### Functional Paradigm

```typescript filename="src/http/server.ts"
import { exis } from 'exisjs'
import { catchError } from 'exisjs/middleware'

export class DatabaseConnectionError extends Error {
  constructor(message: string) {
    super(message)
    this.name = 'DatabaseConnectionError'
  }
}

export default exis({
  async onStart(app) {
    // Globally intercept DatabaseConnectionError
    app.use(catchError(DatabaseConnectionError, (err, req, res) => {
      res.status(503).json({
        success: false,
        error: { code: 'DB_OFFLINE', message: err.message }
      })
    }))
  }
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/server.ts"
import { Server } from 'exisjs/decorators'
import { catchError } from 'exisjs/middleware'
import type { App } from 'exisjs'

export class DatabaseConnectionError extends Error {
  constructor(message: string) {
    super(message)
    this.name = 'DatabaseConnectionError'
  }
}

@Server()
export default class RootServer {
  async onStart(app: App) {
    // Globally intercept DatabaseConnectionError
    app.use(catchError(DatabaseConnectionError, (err, req, res) => {
      res.status(503).json({
        success: false,
        error: { code: 'DB_OFFLINE', message: err.message }
      })
    }))
  }
}
```

This prevents you from having to write `try/catch` blocks in every single route just to handle standard database failures.

### 2. Local Error Hooks (`onError`)

If you want to catch errors only within a specific module or route grouping, you can use the `onError` hook directly in your controller definition.

When a controller throws an error, the local `onError` hook will intercept it before it reaches the global error handler.

### Functional Paradigm

```typescript filename="src/http/users/route.ts"
import { controller, route } from 'exisjs/router'

export default controller({
  // This local hook catches errors thrown by the routes in this controller
  onError: (err, req, res) => {
    console.log('Users Controller Error Handler Caught:', err.message)
    res.status(400).json({ success: false, localError: err.message })
  },

  crash: route.get('/crash', async () => {
    // This error will be caught by the local onError hook
    throw new Error("Something went wrong in the users module")
  })
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/users/route.ts"
import { Controller, Get, UseFilters } from 'exisjs/decorators'
import type { Request, Response } from 'exisjs/router'

function localErrorHandler(err: any, req: Request, res: Response, next: any) {
  console.log('Users Controller Error Handler Caught:', err.message)
  res.status(400).json({ success: false, localError: err.message })
}

@Controller()
@UseFilters(localErrorHandler)
export default class UsersController {
  @Get('/crash')
  async crash() {
    throw new Error("Something went wrong in the users module")
  }
}
```

By combining Exception Filters and Local Error Hooks, ExisJS gives you control over your error boundaries.

## Observability (BYOM/BYOT)

ExisJS ships with tracing and metric adapters. Instead of tying you to a specific telemetry ecosystem, ExisJS lets you **Bring Your Own Metrics** (BYOM) and **Bring Your Own Tracer** (BYOT).

### Metrics

You can use the `metrics` middleware to track request durations and counts.

### Functional Paradigm

```typescript filename="src/http/boundary.ts"
import { defineBoundary } from 'exisjs/router'
import { metrics } from 'exisjs/observability'

const myPrometheusAdapter = {
  onRequestStart: ({ method, path }) => {
    // A request just started. Start a timer.
    return ({ statusCode, durationMs }) => {
      // The request just finished. Push to Prometheus.
      console.log(`[Metrics] ${method} ${path} took ${durationMs}ms with status ${statusCode}`)
    }
  }
}

export const config = defineBoundary({
  middleware: [metrics(myPrometheusAdapter)]
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/boundary.ts"
import { Boundary } from 'exisjs/decorators'
import { metrics } from 'exisjs/observability'

const myPrometheusAdapter = {
  onRequestStart: ({ method, path }) => {
    return ({ statusCode, durationMs }) => {
      console.log(`[Metrics] ${method} ${path} took ${durationMs}ms with status ${statusCode}`)
    }
  }
}

@Boundary({
  middleware: [metrics(myPrometheusAdapter)]
})
export default class RootBoundary {}
```

*Note: ExisJS normalizes dynamic paths (e.g., turning `/users/123` into `/users/:id`) to prevent metrics cardinality issues.*

### OpenTelemetry Tracing

ExisJS seamlessly integrates with OpenTelemetry (OTel) via the `tracing` middleware.

### Functional Paradigm

```typescript filename="src/http/boundary.ts"
import { defineBoundary } from 'exisjs/router'
import { tracing } from 'exisjs/observability'

const myOtelAdapter = {
  startActiveSpan: (name, metadata, callback) => {
    // Create an OTel span
    const span = tracer.startSpan(name)
    // Run the callback and pass the span proxy
    callback({
      setAttribute: (k, v) => span.setAttribute(k, v),
      setStatus: (status) => span.setStatus(status),
      recordException: (e) => span.recordException(e),
      end: () => span.end()
    })
  }
}

export const config = defineBoundary({
  middleware: [tracing(myOtelAdapter)]
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/boundary.ts"
import { Boundary } from 'exisjs/decorators'
import { tracing } from 'exisjs/observability'

const myOtelAdapter = {
  startActiveSpan: (name, metadata, callback) => {
    const span = tracer.startSpan(name)
    callback({
      setAttribute: (k, v) => span.setAttribute(k, v),
      setStatus: (status) => span.setStatus(status),
      recordException: (e) => span.recordException(e),
      end: () => span.end()
    })
  }
}

@Boundary({
  middleware: [tracing(myOtelAdapter)]
})
export default class RootBoundary {}
```

By providing these standard interfaces natively, your application metrics and traces are bound to the ExisJS router lifecycle.
