# Validation & Schemas

If you are coming from frameworks like Fastify, you are likely used to writing validation schemas using JSON Schema strings and relying on external dependencies like AJV.

ExisJS takes a strictly-typed approach. It includes a native validation engine out of the box, powered by Rust for maximum performance. You don't need any external dependencies, and you avoid string-based references.

## The Native Validator (`tex`)

ExisJS exports a global validator object `tex` that allows you to fluently build complex validation schemas using pure, typesafe JavaScript.

```typescript filename="example.ts"
import { tex } from 'exisjs/validator'

// Build a strict schema intuitively
const userSchema = tex.object({
  name: tex.string({ min: 3 }),
  age: tex.number({ optional: true }),
  role: tex.enum(['admin', 'user']),
  email: tex.email()
})

// You can natively parse data directly!
const safeData = userSchema.parse(rawInput)
```

### Validation Primitives

ExisJS supports a comprehensive set of strict validation primitives:

- `tex.string()` - String validation (supports options like `{ min, max, trim, toLowerCase, toUpperCase, escapeHtml, stripHtml, slugify, mask, default }`).
- `tex.email()` - Validates standard email formatting (supports `{ trim, toLowerCase, mask, default }`).
- `tex.uuid()` - Validates UUID strings (supports `{ version: 1 | 4, default }`).
- `tex.cuid()` - Validates CUID identifiers (supports `{ default }`).
- `tex.password()` - Validates password complexity (`{ min, max, requireNumbers, requireSymbols, requireUppercase, requireLowercase }`).
- `tex.creditCard()` - Validates credit card number formats with optional masking (`{ mask: true }`).
- `tex.number()` - Strict number validation (fails if passed a string unless `coerce: true`).
- `tex.number({ coerce: true, min: 0, max: 100, default: 10 })` - Automatically coerces incoming string representations (e.g., query params) into native numbers with optional default fallback.
- `tex.boolean()` - Strict boolean validation.
- `tex.boolean({ coerce: true, default: false })` - Coerces `"true"`/`"1"` and `"false"`/`"0"` into native booleans.
- `tex.date()` - Strict Date instance validation.
- `tex.date({ coerce: true, minDate: '2020-01-01', maxDate: '2030-01-01', default: () => new Date() })` - Automatically parses ISO 8601 strings, UNIX timestamps, or date strings into native JavaScript `Date` objects with optional boundary checks and lazy default factories.
- `tex.array(schema, { coerce: true, min: 1, max: 10, default: [] })` - Validates an array of items. When `{ coerce: true }` is enabled, automatically converts single items or comma-separated query strings (`"apple,banana"`) into typed arrays. Accepts primitive types, `tex.object(...)`, or shorthand plain objects `{ ... }`.
- `tex.enum(['admin', 'user'], { default: 'user' })` - Ensures the value matches one of the provided exact strings.
- `tex.literal(value)` - Validates against an exact primitive literal (`string | number | boolean`).
- `tex.record(schema)` - Validates a dictionary/record of key-value pairs matching the value schema.
- `tex.any()` - Allows any payload value without constraint.
- `tex.file({ maxSize: 5 * 1024 * 1024, mimeTypes: ['image/png', 'image/jpeg'] })` - Validates uploaded file payloads (size and MIME type).
- `tex.object({ ... })` - Validates structured JSON objects.

All primitives accept modifier options or chained helper methods:
- `.optional()` / `{ optional: true }` - Allows `undefined`.
- `.nullable()` / `{ nullable: true }` - Allows `null`.
- `.nullish()` / `{ nullish: true }` - Allows both `null` and `undefined`.
- `{ default: value | (() => value) }` - Provides a static default or dynamic factory function when the field is omitted or `undefined`. Automatically marks the field as optional in schemas and infers concrete types in TypeScript.

> [!TIP]
> **Unified Defaults without Method Chaining**: ExisJS avoids `.default()` chaining overhead in favor of declarative options objects (e.g. `tex.number({ default: 3000 })` or `tex.date({ default: () => new Date() })`). Dynamic factory functions evaluate per request so timestamps and UUIDs remain fresh!

> [!TIP]
> **Automatic Empty String `""` Normalization**: When forms or query parameters pass empty strings `""` for fields marked as `.optional()`, `.nullable()`, or `.nullish()`, ExisJS automatically converts them to `undefined` or `null` before running type validation. This prevents false positive type errors on numeric, UUID, or enum fields!

### Data Sanitization (Trimming & Formatting)

ExisJS allows you to mutate and sanitize incoming data in real-time before it reaches your controller. It includes a native Rust-powered sanitization engine for Strings and Arrays.

```typescript filename="example.ts"
import { tex } from 'exisjs/validator'
import { sanitize } from 'exisjs/sanitize'

const loginSchema = tex.object({
  // Automatically trim whitespace, convert to lowercase, and prevent HTML injections
  email: tex.email().sanitize(sanitize.trim, sanitize.toLowerCase, sanitize.escapeHtml),
  password: tex.string({ min: 8 })
})

const articleSchema = tex.object({
  title: tex.string().sanitize(sanitize.collapseWhitespace, sanitize.truncate(100)),
  // Auto-generate slugs from the title using sanitize.slugify!
  slug: tex.string().sanitize(sanitize.slugify),
  tags: tex.array(tex.string()).sanitize(sanitize.dedupe, sanitize.compact)
})
```

### Standalone Sanitization Usage

Because the sanitization engine is designed as a collection of pure, independent functions, **you don't have to use it with the Validator**. If you ever need to manually sanitize data deep inside your services, background jobs, or generic Node.js scripts, you can import the engine directly:

```typescript filename="src/services/formatter.ts"
import { sanitize } from 'exisjs/sanitize'

export function formatArticleTitle(rawInput: string) {
  let clean = sanitize.stripHtml(rawInput)
  clean = sanitize.collapseWhitespace(clean)
  return sanitize.trim(clean)
}
```

## Schema Composition & Features

ExisJS validation provides robust features to handle real-world use cases efficiently and seamlessly.

### Schema Composition

You can construct powerful shared schemas easily using composition methods (`.partial()`, `.omit()`, `.pick()`). This prevents schema duplication.

```typescript filename="example.ts"
const UserSchema = tex.object({
  id: tex.string(),
  name: tex.string(),
  email: tex.email(),
  password: tex.string({ min: 8 })
})

// Create an update schema (all fields optional)
const UpdateUserSchema = UserSchema.partial()

// Create a safe response schema (omit password)
const PublicUserSchema = UserSchema.omit(['password'])

// Create a specialized schema
const LoginSchema = UserSchema.pick(['email', 'password'])

// Chain multiple schemas using tex.union()
const FlexibleIdSchema = tex.union([tex.string(), tex.number()])
```

### Asynchronous Validation

Need to check a database during validation? No problem! Use `.refineAsync()` to run complex async logic seamlessly within your validation schemas. The ExisJS router will automatically wait for the async checks to resolve before executing your route handler.

```typescript filename="example.ts"
const registerSchema = tex.object({
  email: tex.email()
    .refineAsync(async (val) => {
      const exists = await db.users.find({ email: val })
      return !exists // Return false if email is taken
    }, 'Email is already taken'),
  password: tex.string({ min: 8 })
})
```

### Response Stripping & Serialization

Because `TexEngine` validates by strictly iterating over its defined schema keys, it naturally **strips** any extra or unknown properties from the resulting object. 

This provides immense security out of the box when used as a `response` schema, ensuring you never accidentally leak sensitive data (like passwords or internal IDs) to the client. The ExisJS router handles this stripping serialization natively behind the scenes.

### Separating Schemas

To keep your route files clean and maintainable, we highly recommend defining your schemas in a dedicated `schema.ts` file alongside your routes.

```typescript filename="src/http/users/schema.ts"
import { tex } from 'exisjs/validator'
import type { ResolveSchema } from 'exisjs/validator'

export const UserParamsSchema = tex.object({
  id: tex.number({ coerce: true })
})

export type UserParams = ResolveSchema<typeof UserParamsSchema>
```

To validate incoming HTTP requests, ExisJS provides built-in validation configurations. Whether you use the Functional paradigm or the Class-based (OOP) paradigm, ExisJS validates incoming payloads and types your handlers.

#### Functional Paradigm

```typescript filename="src/http/users/route.ts"
import { controller, route } from 'exisjs/router'
import { tex } from 'exisjs/validator'

export default controller({
  create: route.post('/', {
    // 1. The validation schema is passed directly in the config
    body: tex.object({
      username: tex.string({ min: 4 }),
      password: tex.string({ min: 8 })
    }),
    query: tex.object({
      source: tex.string({ optional: true })
    }),
      
    // 2. Your handler only runs if validation succeeds
    async handle({ body, query, req, res }) {
      // body and query are strongly-typed here
      await db.users.create(body)
      res.status(201).json({ success: true })
    }
  })
})
```

#### Class-Based (OOP) Paradigm

```typescript filename="src/http/api/books/route.ts"
import { Controller, Use, Post, Body, Req } from 'exisjs/decorators'
import { tex } from 'exisjs/validator'
import type { ResolveSchema } from 'exisjs/validator'

// 1. Define your schema
const CreateBookSchema = tex.object({
  title: tex.string(),
  caption: tex.string(),
  rating: tex.number(),
  image: tex.string(),
})

// 2. Infer the TypeScript type!
type CreateBookDto = ResolveSchema<typeof CreateBookSchema>

@Use(protectRoute)
@Controller()
export default class BooksController {
  
  // 3. Inject the schema directly into the @Body() decorator!
  @Post('/')
  async create(@Body(CreateBookSchema) body: CreateBookDto, @Req() req: any) {
    // If validation fails, this block is never reached!
    // body is strictly typed as CreateBookDto
    
    const newBook = new Book({
      title: body.title,
      caption: body.caption,
      rating: body.rating,
      image: body.image,
      user: req.user._id,
    })

    await newBook.save()
    return newBook
  }
}
```


### Nested Sub-Documents & Array Schemas

ExisJS natively validates arbitrarily deep sub-documents and nested arrays off-heap with Rust acceleration:

```typescript filename="src/http/users/schema.ts"
import { tex } from 'exisjs/validator'

export const RegisterUserSchema = tex.object({
  username: tex.string({ min: 3 }),
  profile: tex.object({
    bio: tex.string().nullish(), // allows undefined, null, or ""
    avatarUrl: tex.string({ optional: true }),
    socials: tex.object({
      twitter: tex.string({ optional: true }),
      github: tex.string({ optional: true }),
    }),
    tags: tex.array(tex.string({ min: 2 })),
  }),
  // You can use tex.object(...) OR a plain object schema shorthand!
  items: tex.array({
    sku: tex.string(),
    quantity: tex.number({ min: 1 }),
  }),
})
```

#### First-Class Form & Multipart Support
- **Single-Object Coercion**: When HTML forms or mobile clients submit a single item instead of an array (e.g. `{ items: { sku: "ABC", quantity: 1 } }`), the Rust engine automatically coerces it into a single-element array `[ { sku: "ABC", quantity: 1 } ]` rather than throwing `"Must be an array"`.
- **Stringified JSON Support**: When submitting `multipart/form-data`, stringified JSON arrays (e.g. `items: "[{\"sku\":\"ABC\",\"quantity\":2}]"`) or stringified objects are automatically deserialized and validated.
- **Type Inference**: TypeScript automatically infers the shape of array elements for both `tex.array(tex.object(...))` and `tex.array({ ... })`, ensuring full autocomplete without falling back to `never`.

### Query String Array & Date Coercion

Query strings in HTTP cannot natively represent arrays or date instances. ExisJS solves this elegantly through `{ coerce: true }`:

#### Functional Paradigm

```typescript filename="src/http/events/route.ts"
import { controller, route } from 'exisjs/router'
import { tex } from 'exisjs/validator'

const FilterSchema = tex.object({
  // Coerces ISO 8601 strings (?from=2026-09-01T00:00:00Z) into Date instances
  from: tex.date({ coerce: true, optional: true }),
  to: tex.date({ coerce: true, optional: true }),
  
  // Coerces both comma-separated strings (?tags=tech,ai) AND repeated params (?tags=tech&tags=ai)
  // or single values (?tags=tech -> ['tech']) into a typed array of strings
  tags: tex.array(tex.string(), { coerce: true, optional: true }),

  // Numbers within comma-separated arrays (?ids=1,2,3 -> [1, 2, 3]) are also coerced
  ids: tex.array(tex.number({ coerce: true }), { coerce: true, optional: true })
})

export default controller({
  listEvents: route.get('/events', {
    query: FilterSchema,
    handle({ query, res }) {
      // query.from is Date | undefined
      // query.tags is string[] | undefined
      // query.ids is number[] | undefined
      res.json({ filter: query })
    }
  })
})
```

#### Class-Based (OOP) Paradigm

```typescript filename="src/http/events/route.ts"
import { Controller, Get, Query } from 'exisjs/decorators'
import { tex } from 'exisjs/validator'
import type { ResolveSchema } from 'exisjs/validator'

const FilterSchema = tex.object({
  from: tex.date({ coerce: true, optional: true }),
  to: tex.date({ coerce: true, optional: true }),
  tags: tex.array(tex.string(), { coerce: true, optional: true }),
  ids: tex.array(tex.number({ coerce: true }), { coerce: true, optional: true }),
})

type FilterDto = ResolveSchema<typeof FilterSchema>

@Controller('/events')
export default class EventsController {
  @Get('/', { query: FilterSchema })
  listEvents(@Query() query: FilterDto) {
    return { filter: query }
  }
}
```

## Pagination Schemas (`tex.pagination`)

ExisJS provides a dedicated schema primitive for query pagination. It automatically coerces incoming string query parameters (`?page=2&limit=25&sort=name&order=asc`) into typed numbers and strings while enforcing sensible bounds:

#### Functional Paradigm

```typescript filename="src/http/items/route.ts"
import { controller, route } from 'exisjs/router'
import { tex, paginate, getPaginationSkip } from 'exisjs/validator'

const ItemQuerySchema = tex.pagination({
  defaultLimit: 20, // Default items per page if omitted
  maxLimit: 100,    // Hard cap to prevent memory exhaustion
})

export default controller({
  list: route.get('/', {
    query: ItemQuerySchema,
    async handle({ query }) {
      const { skip, limit, page } = getPaginationSkip(query)
      const items = await fetchItems({ skip, limit, sort: query.sort, order: query.order })
      const total = await countItems()
      
      return paginate(items, total, { page, limit })
    }
  })
})
```

#### Class-Based (OOP) Paradigm

```typescript filename="src/http/items/route.ts"
import { Controller, Get, Query } from 'exisjs/decorators'
import { tex, paginate, getPaginationSkip } from 'exisjs/validator'

const ItemQuerySchema = tex.pagination({
  defaultLimit: 20,
  maxLimit: 100,
})

@Controller('/items')
export default class ItemsController {
  @Get('/', { query: ItemQuerySchema })
  async list(@Query() query: any) {
    const { skip, limit, page } = getPaginationSkip(query)
    const items = await fetchItems({ skip, limit, sort: query.sort, order: query.order })
    const total = await countItems()

    return paginate(items, total, { page, limit })
  }
}
```

## Error Handling & Developer Diagnostics

If a request fails validation, ExisJS intercepts the rejection and returns a standardized `400 Bad Request` containing both a legacy `errors: Record<string, string>` dictionary and a structured `details: ValidationErrorDescriptor[]` array for frontend form field mapping:

```json filename="HTTP 400 Bad Request Response"
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Validation Error: username: Field must be at least 4 characters, profile.tags: Expected array of strings",
  "errors": {
    "username": "Field must be at least 4 characters",
    "profile.tags": "Expected array of strings"
  },
  "details": [
    {
      "path": "username",
      "message": "Field must be at least 4 characters",
      "expected": "min: 4",
      "received": "abc",
      "code": "VALUE_TOO_SMALL"
    },
    {
      "path": "profile.tags",
      "message": "Expected array of strings",
      "expected": "Array of string",
      "received": "number",
      "code": "INVALID_TYPE"
    }
  ]
}
```

### Dev Mode Terminal Diagnostics

When validation fails in development mode, ExisJS prints an immediate tabular diagnostic to your terminal displaying the HTTP method, route path, failing HTTP part (`body`, `query`, `params`, `headers`), exact field path, received value, and expected schema constraint:

```text
[VALIDATION FAILED] POST /api/v1/visits (part: body)
┌─────────────┬───────────────────────────┬──────────────────┐
│ Field       │ Received                  │ Expected         │
├─────────────┼───────────────────────────┼──────────────────┤
│ phone       │ "123"                     │ min: 7, max: 20  │
│ idProofs    │ "[object Object]"         │ Array of IDProof │
└─────────────┴───────────────────────────┴──────────────────┘
```

## Environment Variable Validation (`tex.env`)

Because `process.env` always supplies raw string values (e.g. `"4000"`, `"true"`, `"1"`), ExisJS includes a dedicated `tex.env()` schema parser. It automatically injects coercion for numbers, booleans, dates, and arrays, allowing you to validate your environment variables on boot without writing `{ coerce: true }` on every field:

```typescript filename="src/config/env.ts"
import { tex } from 'exisjs/validator'

export const env = tex.env({
  PORT: tex.number({ default: 4000 }), // Automatically coerced from "4000" -> 4000
  DEBUG: tex.boolean({ default: false }), // Parsed from "true" | "1" | "false" | "0"
  DATABASE_URL: tex.string(),
  JWT_SECRET: tex.string({ min: 32 }),
  ALLOWED_ORIGINS: tex.array(tex.string()), // Parsed from "http://localhost:3000,https://app.com"
  NODE_ENV: tex.enum(['development', 'production', 'test'] as const, {
    default: 'development',
  }),
}).parse(process.env)
```

> [!TIP]
> **Zero-Boilerplate Boot Safety**: `tex.env()` automatically validates `process.env` on server startup. If a required environment variable is missing, it crashes immediately with a clean diagnostic log before the HTTP listener opens.

## Third-Party Validator Interoperability (Zod, Valibot, ArkType)

While ExisJS provides the high-performance native `tex` engine out of the box, it is **100% interoperable with external schema libraries like Zod, Valibot, or ArkType** via Duck Typing.

Any object with a `.parse()` or `.safeParse()` method can be passed directly as a route schema or used in `src/config/env.ts`.

### Using Zod in Routes

#### Functional Paradigm

```typescript filename="src/http/users/route.ts"
import { controller, route } from 'exisjs/router'
import { z } from 'zod'

const CreateUserSchema = z.object({
  name: z.string().min(3),
  email: z.string().email(),
  role: z.enum(['admin', 'user']),
})

export default controller({
  create: route.post('/', {
    body: CreateUserSchema, // 👈 Directly pass your Zod schema!
    async handle({ body, res }) {
      return res.status(201).json({ success: true, user: body })
    }
  })
})
```

#### Class-Based (OOP) Paradigm

```typescript filename="src/http/users/route.ts"
import { Controller, Post, Body, HttpCode } from 'exisjs/decorators'
import { z } from 'zod'

const CreateUserSchema = z.object({
  name: z.string().min(3),
  email: z.string().email(),
  role: z.enum(['admin', 'user']),
})

type CreateUserDto = z.infer<typeof CreateUserSchema>

@Controller('/users')
export default class UsersController {
  @Post('/')
  @HttpCode(201)
  async create(@Body(CreateUserSchema) body: CreateUserDto) {
    return { success: true, user: body }
  }
}
```

### Using Zod for Environment Validation

```typescript filename="src/config/env.ts"
import { z } from 'zod'

const EnvSchema = z.object({
  PORT: z.coerce.number().default(4000),
  NODE_ENV: z.enum(['development', 'production', 'test']).default('development'),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
})

export const env = EnvSchema.parse(process.env)
```

> [!NOTE]
> **Universal Error Normalization**: Regardless of which library you use (**Zod**, **Valibot**, **Yup**, **Joi**, **ArkType**, or any Standard Schema-compliant library), ExisJS inspects the error structure (`issues`, `errors`, `inner`) and automatically normalizes it into standardized `400 Bad Request` JSON responses with complete field mappings and dev-mode terminal overlays.
