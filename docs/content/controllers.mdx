# Controllers

Controllers are responsible for handling incoming requests and sending responses back to the client.

A controller's purpose is to handle specific requests for the application. The routing mechanism determines which controller will handle each request. Often, a controller has multiple routes, and each route can perform a different action.

While ExisJS natively supports Functional Routing, developers coming from enterprise backgrounds often prefer Object-Oriented patterns. To create a basic OOP controller, we use classes and decorators. Decorators link classes with the necessary metadata, allowing ExisJS to automatically route requests.

## Routing & Prefixes

In the following example, we'll use the `@Controller()` decorator, which is required to define a basic OOP controller. We'll specify an optional route path prefix of `users`. Using a path prefix helps group related routes together.

```typescript filename="src/http/users/route.ts"
import { Controller, Get } from 'exisjs/decorators'

@Controller('users')
export default class UsersController {
  @Get()
  findAll(): any[] {
    return [
      { id: 1, name: 'Alice' },
      { id: 2, name: 'Bob' }
    ]
  }
}
```

The `@Get()` HTTP request method decorator placed before the `findAll()` method tells ExisJS to create a handler for GET requests. Because the controller has a prefix of `users`, this endpoint maps to `GET /users`. If we used `@Get('active')`, it would map to `GET /users/active`.

## Request Object

Handlers often need access to the client’s request details. You can access the request object by injecting it using the `@Req()` decorator.

```typescript filename="src/http/users/route.ts"
import { Controller, Get, Req } from 'exisjs/decorators'
import type { Request } from 'exisjs/router'

@Controller('users')
export default class UsersController {
  @Get()
  findAll(@Req() request: Request): any[] {
    console.log(request.ip, request.headers)
    return []
  }
}
```

In most cases, you don't need to manually access the entire request object. Instead, you can use dedicated decorators provided out of the box:

## Payloads & Validation

For POST, PUT, and PATCH endpoints, you can validate and read incoming payloads using either method-level schemas or parameter-level `@Body(Schema)` decorators:

```typescript filename="src/http/users/route.ts"
import { Controller, Post, Body, HttpCode } from 'exisjs/decorators'
import { tex } from 'exisjs/validator'
import type { ResolveSchema } from 'exisjs/validator'

export const CreateUserSchema = tex.object({
  name: tex.string({ min: 2 }),
  email: tex.email(),
  role: tex.enum(['admin', 'user'], { default: 'user' }),
})

export type CreateUserDto = ResolveSchema<typeof CreateUserSchema>

@Controller('users')
export default class UsersController {
  // 1. Parameter-level validation schema
  @Post('/')
  @HttpCode(201)
  async create(@Body(CreateUserSchema) dto: CreateUserDto) {
    return { id: 3, ...dto }
  }

  // 2. Or method-level schema object
  @Post('/raw', { body: CreateUserSchema })
  async createWithMethodSchema(@Body() dto: CreateUserDto) {
    return { id: 4, ...dto }
  }
}
```

## Dependency Injection in Controllers

Controllers can inject services using either the ergonomic `inject()` helper or standard constructor injection:

```typescript filename="src/http/users/route.ts"
import { Controller, Get, Param } from 'exisjs/decorators'
import { inject, Inject, Optional } from 'exisjs/di'
import { UsersService } from './service'

@Controller('users')
export default class UsersController {
  // Approach A: Property-level injection (Recommended)
  private usersService = inject(UsersService)

  // Approach B: Constructor injection
  constructor(
    @Inject('DATABASE_URL') private dbUrl: string,
    @Optional() @Inject('METRICS') private metrics?: any
  ) {}

  @Get('/:id')
  async getUser(@Param('id') id: string) {
    return this.usersService.findById(id)
  }
}
```

## File Uploads

You can process file uploads in OOP controllers using `@UseUpload` or `@Upload` decorators alongside `@UploadedFile()` and `@UploadedFiles()`:

```typescript filename="src/http/users/route.ts"
import { Controller, Post, UseUpload, UploadedFile, Body } from 'exisjs/decorators'
import type { UploadedFile as IUploadedFile } from 'exisjs/router'

@Controller('users')
export default class UsersController {
  @Post('/avatar')
  @UseUpload({
    field: 'avatar',
    maxBytes: 5 * 1024 * 1024,
    mimeTypes: ['image/jpeg', 'image/png', 'image/webp'],
  })
  async uploadAvatar(
    @UploadedFile() file: IUploadedFile,
    @Body() body: { caption?: string }
  ) {
    return {
      success: true,
      filename: file.filename,
      size: file.size,
      caption: body.caption,
    }
  }
}
```

## Streaming & Downloads

OOP controllers support all streaming features including Node.js `Readable` streams, Web `ReadableStream`, async generators, and file downloads:

```typescript filename="src/http/files/route.ts"
import { Controller, Get, Res } from 'exisjs/decorators'
import type { Response } from 'exisjs/router'
import fs from 'node:fs'

@Controller('files')
export default class FilesController {
  // 1. Force file download
  @Get('/download')
  download(@Res() res: Response) {
    res.download('./reports/annual.pdf', 'Annual-Report.pdf')
  }

  // 2. Stream Node.js Readable or auto-pipe return value
  @Get('/stream')
  streamCsv() {
    return fs.createReadStream('./data/export.csv')
  }

  // 3. Server-Sent Events (SSE)
  @Get('/events')
  events(@Res() res: Response) {
    const sse = res.sse()
    sse.send({ event: 'ping', data: { time: Date.now() } })
  }
}
```

## Status Codes & Headers

By default, responses have a `200 OK` status (except POST which uses `201`). You can change this declaratively using the `@HttpCode()` and `@Header()` decorators.

```typescript filename="src/http/users/route.ts"
import { Controller, Post, HttpCode, Header } from 'exisjs/decorators'

@Controller('users')
export default class UsersController {
  @Post()
  @HttpCode(204)
  @Header('Cache-Control', 'no-store')
  create() {
    return null // No Content
  }
}
```

## Extended Features

ExisJS provides routing enhancements like Subdomain Routing, Redirects, and Passthrough Responses. These are supported across both paradigms.

### Functional Paradigm

```typescript filename="src/http/advanced/route.ts"
import { controller, route } from 'exisjs/router'

export default controller({
  // 1. Subdomain Routing
  ping: route.get('/ping', {
    host: ':sub.exis.local',
    handle({ req }) {
      return { subdomain: (req.params as any).sub }
    }
  }),
  // 2. Redirect
  redirect: route.get('/redirect', {
    handle({ res }) {
      res.redirect('https://google.com')
    }
  }),
  // 3. Passthrough Response
  manual: route.get('/manual', {
    handle({ res }) {
      res.setHeader('X-Custom', 'true')
      return { msg: 'This is auto-serialized with custom headers!' }
    }
  })
})
```

### Class-Based (OOP) Paradigm

```typescript filename="src/http/advanced/route.ts"
import { Controller, Get, HostParam, Redirect, Res } from 'exisjs/decorators'
import type { Response } from 'exisjs/router'

// 1. Subdomain Routing
@Controller({ host: ':sub.exis.local' })
export class SubdomainController {
  @Get('/ping')
  ping(@HostParam('sub') sub: string) {
    return { subdomain: sub }
  }
}

@Controller('users')
export class AdvancedController {
  // 2. Redirect
  @Get('/redirect')
  @Redirect('https://google.com')
  redirect() {}

  // 3. Passthrough Response
  @Get('/manual')
  manual(@Res({ passthrough: true }) res: Response) {
    res.setHeader('X-Custom', 'true')
    return { msg: 'This is auto-serialized with custom headers!' }
  }
}
```

## Registration & Library-Specific Response

Unlike frameworks where controllers must be registered manually in a module file, ExisJS uses Folder-Based Routing. To register a controller, you export default the class inside a `route.ts` file.

If you need low-level control over the response, you can inject the native `@Res()` object.

```typescript filename="src/http/users/route.ts"
import { Controller, Get, Res } from 'exisjs/decorators'
import type { Response } from 'exisjs/router'

@Controller('users')
export default class UsersController {
  @Get()
  findAll(@Res() res: Response) {
    res.status(200).json({ data: [] })
  }
}
```

## Controller Inheritance (Base & Abstract Controllers)

ExisJS supports full OOP inheritance for controllers. You can create generic base or abstract CRUD controllers and inherit all route handlers, parameter decorators, middlewares, guards, interceptors, and filters down to subclasses:

```typescript filename="src/http/base-crud.controller.ts"
import { Get, Post, Delete, Param, Body } from 'exisjs/decorators'

export abstract class BaseCrudController<T> {
  protected abstract resourceName: string

  @Get('/')
  async findAll(): Promise<T[]> {
    return []
  }

  @Get('/:id')
  async findById(@Param('id') id: string): Promise<T> {
    return { id, resource: this.resourceName } as any
  }

  @Delete('/:id')
  async remove(@Param('id') id: string): Promise<{ deleted: boolean }> {
    return { deleted: true }
  }
}
```

Subclasses inherit all parent endpoints and can add new routes or selectively override base methods:

```typescript filename="src/http/users/route.ts"
import { Controller, Post, Body, Param } from 'exisjs/decorators'
import { BaseCrudController } from '../base-crud.controller'

export interface User {
  id: string
  name: string
}

@Controller('/users')
export default class UsersController extends BaseCrudController<User> {
  protected resourceName = 'users'

  // Subclass defines additional route
  @Post('/')
  async create(@Body() user: User) {
    return { created: true, user }
  }

  // Subclass can override inherited remove handler
  override async remove(@Param('id') id: string) {
    return { deleted: true, id, customAudit: true }
  }
}
```

### Functional Controller Inheritance (`controller.extend`)

In the functional paradigm, inheritance is achieved via `controller.extend(base, overrides)`. This inherits all route handlers, lifecycle hooks, and middlewares from a base controller factory and allows overriding endpoints or adding new routes with full type inference:

```typescript filename="src/http/products/route.ts"
import { controller, route } from 'exisjs/router'

// 1. Generic functional base CRUD controller
function createBaseCrud(resourceName: string) {
  return controller({
    list: route.get('/', {
      async handle() {
        return { resource: resourceName, items: [] }
      }
    }),
    getById: route.get('/:id', {
      async handle({ params }) {
        return { resource: resourceName, id: params.id }
      }
    }),
    remove: route.delete('/:id', {
      async handle({ params }) {
        return { deleted: true, id: params.id }
      }
    })
  })
}

// 2. Extend base controller with overrides and additional routes
export default controller.extend(createBaseCrud('products'), {
  // Additional specialized route
  featured: route.get('/featured', {
    async handle() {
      return { featured: ['Product 1', 'Product 2'] }
    }
  }),

  // Override base endpoint
  getById: route.get('/:id', {
    async handle({ params }) {
      return { customProduct: true, id: params.id }
    }
  })
})
```

## Functional Controller Composition (`controller.merge`)

When a single `route.ts` manages a feature area with multiple concerns (for example, auth flows containing credentials, sessions, and OAuth), `controller.merge(...controllers)` allows splitting logic into modular controller objects and merging them into a single default export:

```typescript filename="src/http/auth/route.ts"
import { controller, route } from 'exisjs/router'

// 1. Modular controller for password authentication
const passwordAuth = controller({
  login: route.post('/login', {
    async handle({ body }) {
      return { token: 'jwt-auth-token' }
    }
  }),
  logout: route.post('/logout', {
    async handle() {
      return { success: true }
    }
  })
})

// 2. Modular controller for OAuth providers
const oauthProviders = controller({
  google: route.get('/google', {
    async handle() {
      return { redirectUrl: 'https://accounts.google.com/o/oauth2/auth' }
    }
  }),
  github: route.get('/github', {
    async handle() {
      return { redirectUrl: 'https://github.com/login/oauth/authorize' }
    }
  })
})

// 3. Merge both into the single exported controller for this folder
export default controller.merge(passwordAuth, oauthProviders)
```

```typescript filename="src/http/items/route.ts"
import {
  Controller,
  Get,
  Post,
  Param,
  Query,
  Body,
  UsePipes,
  ParseIntPipe,
  ParseBoolPipe,
  ParseUUIDPipe,
  ParseArrayPipe,
  ValidationPipe,
} from 'exisjs/decorators'

@Controller('/items')
export default class ItemsController {
  // 1. Parameter-level pipe
  @Get('/:id')
  async getItem(@Param('id', ParseIntPipe) id: number) {
    return { id, isNumber: typeof id === 'number' }
  }

  // 2. Query boolean & array pipes
  @Get('/')
  async listItems(
    @Query('active', ParseBoolPipe) active: boolean,
    @Query('ids', new ParseArrayPipe({ items: ParseIntPipe })) ids: number[]
  ) {
    return { active, ids }
  }

  // 3. UUID validation pipe
  @Get('/by-uuid/:uuid')
  async getByUUID(@Param('uuid', ParseUUIDPipe) uuid: string) {
    return { uuid }
  }

  // 4. Method-level or Class-level @UsePipes
  @Post('/')
  @UsePipes(new ValidationPipe({ transform: true }))
  async createItem(@Body() body: any) {
    return { created: true, body }
  }
}
```

<Info title="Tip: Safely Returning with @Res">
In some frameworks, injecting the `@Res()` object disables auto-serialization, causing the request to hang if you forget to call `res.send()`. ExisJS handles this differently: if you return a value from your handler, ExisJS will still safely auto-serialize it to JSON even if you injected `@Res()` to set a custom header.
</Info>
