# Security Policy

The ExisJS team takes the security of the framework and of the applications built with it seriously. Thank you for helping keep ExisJS and its users safe.

## Supported Versions

Security fixes are released for the latest minor version. Before 1.0, upgrade to the newest `0.x` release to receive them.

| Version | Supported          |
| ------- | ------------------ |
| 0.9.x   | :white_check_mark: |
| < 0.9   | :x:                |

This covers the packages published from this repository: `exisjs`, `create-exisjs` and `@exisjs/fetch`.

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues, discussions or pull requests.**

Report them privately through GitHub:

1. Go to the [**Security** tab](https://github.com/v25group/exisjs/security) of this repository.
2. Click **Report a vulnerability** ([direct link](https://github.com/v25group/exisjs/security/advisories/new)).
3. Fill in the form. Only you and the maintainers can see the report.

You need a GitHub account; no email is required. The report becomes a private security advisory where we can discuss the issue with you, work on a fix in a private fork, and request a CVE.

### What to Include

The more of this you can give us, the faster we can confirm and fix the issue:

- The affected package and version, and the relevant configuration (`exis.config.ts` options, engine, Node.js version).
- The type of issue (for example request smuggling, path traversal, authorization bypass, prototype pollution, denial of service).
- Step-by-step instructions to reproduce it, ideally a minimal proof of concept.
- The impact: what an attacker can do and under which conditions.
- Any known workaround.

## What Happens Next

| Step | Target time |
| :--- | :--- |
| We acknowledge your report | Within 3 business days |
| We confirm or rule out the issue and share our assessment of severity | Within 10 business days |
| We release a fix | Depends on complexity; we keep you updated at least every 2 weeks |

1. We confirm the problem and determine the affected versions.
2. We prepare a fix and release it as a new patch version for every supported line.
3. We publish a GitHub Security Advisory (with a CVE where applicable) and a note in the release notes, crediting you unless you ask to remain anonymous.

## Disclosure Policy

We follow coordinated disclosure. Please give us a reasonable time to release a fix before sharing details publicly: we aim to publish within **90 days** of the report, and earlier once a fix is available. If a vulnerability is already being exploited or disclosed publicly, tell us in the report and we will prioritise it.

## Scope

**In scope:** vulnerabilities in the code of the published packages, including their default configuration, for example:

- Bypassing authorization (`@Roles`, `@Permissions`, guards, boundaries) or the request validation layer.
- Request parsing flaws: smuggling, header injection, path traversal in `serveStatic` / `res.download`, prototype pollution through bodies or query strings.
- Denial of service caused by a small number of requests (for example catastrophic regular expression backtracking or unbounded memory use).
- Secrets leaking into responses or logs through framework code.
- Insecure code generated by `create-exisjs`.

**Out of scope:**

- Applications built with ExisJS, unless the cause is in the framework.
- Insecure configuration chosen explicitly by the application (for example `cors: { origin: '*' }` with your own credential handling, or turning off `helmet`).
- The example applications in `examples/`, which are for demonstration.
- Volumetric denial of service (flooding a server with traffic).
- Vulnerabilities in third-party dependencies that do not affect ExisJS in practice. Report those upstream; we track them through Dependabot and `npm audit`.
- Reports produced only by automated scanners without a demonstrated impact.

## Safe Harbor

We will not take legal action against, or ask law enforcement to investigate, anyone who researches and reports a vulnerability in good faith under this policy. Please avoid privacy violations, data destruction and service disruption, and only test against systems you own or are allowed to test.

## Release Integrity

- Packages are published from GitHub Actions with [npm provenance](https://docs.npmjs.com/generating-provenance-statements), so every release on npm links to the commit and workflow that built it. Verify your installed packages with `npm audit signatures`.
- CI runs `npm audit` for production dependencies on every change; a high or critical advisory fails the build.
- Dependencies are kept up to date with Dependabot.

## Security Updates

Security releases are announced in the [GitHub Security Advisories](https://github.com/v25group/exisjs/security/advisories) of this repository and in the [release notes](./CHANGELOG.md). Watch the repository (**Watch → Custom → Security alerts**) to be notified.
